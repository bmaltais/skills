# Writing for Humans

Produce the smallest reading set that lets the intended reader understand the project and act.
Write for a college-educated non-specialist: preserve the substance, explain unfamiliar terms and
put consequences before implementation mechanics.

## 1. Establish the reader and deliverable

Read the [reading guide](./references/reading-guide.md) for document boundaries, word budgets,
plain-language examples, ownership and the Board evidence map.

Resolve the primary audience, questions to answer and requested output: research, templates,
populated briefs or consolidation. Ask only for missing choices that change the work. For a
template-only request, finish with reusable references rather than inventing project facts.

Keep this skill's research, guide and templates bundled here. Put populated project documents
in the repository's agreed location only when requested. A new reading layer is a proposal,
not permission to move, delete or rewrite the technical library.

**Done when:** the reader, their questions, deliverables and destination are explicit.

## 2. Establish the evidence

Follow the repository's documentation discovery and change workflow. Select the sources owning
requirements, architecture rules, decision outcomes and delivery evidence. The guide's Board
map is a starting point; recheck source dates and content on each use.

For framework rationale or a research refresh, read the
[primary-source comparison](./references/research.md). Verify new external claims against their
first-party sources and distinguish those claims from local recommendations.

Record conflicts and unknowns with an owner and resolution action. Keep intended design, approval,
deployment and observed verification separate; a repository commit establishes only a code change.

**Done when:** every material claim has an owning source or is explicitly unknown; conflicts
are surfaced rather than silently resolved.

## 3. Draft only the needed views

Select the matching block from the [template pack](./references/templates.md): project brief,
architecture overview, optional detailed design or delivery brief. The guide defines which readers
need which views. Reuse an existing owning design before creating a competing one.

Write the answer first, then its practical consequence and supporting link. Explain a product's
job before naming it. A summary communicates the implication of a rule; its link preserves the
authoritative detail. Keep current progress out of the enduring architecture narrative.

**Done when:** the selected template's prompts are resolved, essential limitations remain visible,
and ownership, evidence dates and review dates are supplied or explicitly unresolved.

## 4. Verify and hand over

Apply the template pack's publication check and the repository's safe validation checks. Confirm
that links and section anchors resolve, the selected word budgets are met, and no existing rule
or approval status changed through paraphrase.

For populated briefs, use the guide's reader pilot. Report a human comprehension check as pending
until actual readers complete it; source and formatting checks are not a substitute. For a
template-only deliverable, verify the prompts cover each document's stated completion criterion.

Hand over the reading entry point, what was checked, unresolved questions and any pending approval.
Retain the detailed sources for optional reading.

**Done when:** mechanical checks pass and any unverified human outcome is named, without claiming
the proposed reading system has already been adopted or tested.
